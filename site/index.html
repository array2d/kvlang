Why kvlang

A small core with everything else registered at a path.

Code is data

A function is a subtree. Its parameters are reads on the negative axis and writes on the positive one — the same shape as every value in kvspace. 


    rwfunc add(a:int64, b:int64) -> (c:int64) { a + b -> c }

The PC is a path — crash-resumable

There is no separate call stack. Frame depth is written into the program counter itself, so a restarted process can continue from the same instruction. 


PC    = "/vthread/<vid>/[1]/[3,0]"            vthread vid, frame 1, instruction 3

Small core, extensions on top

The core runtime only executes and branches. Every other opcode is registered at /lib/<opcode> and handed to a runtime that declares it. 


/lib/<opcode>/vids/<vtid> = pc

Byte-identical backends

One PascalCase C ABI, two implementations chosen by DSN. The same program runs against shared memory, files, or Redis with identical bytes. 


KVSPACE=shm:///tmp/kvlang.shm ./bin/kvlang tutorial/01-basics/hello.kv   # kvspace-c
KVSPACE=fs:///tmp/kvlang-fs   ./bin/kvlang tutorial/01-basics/hello.kv   # kvspace-durable

Built for agents

Source, values, and compiled forms are all plaintext in the same tree. deepx uses kvlang as its front-end language; byteseek reads and rewrites its own code and state through the same KV reads and writes.

Ecosystem

Three layers, one tree. Each layer is independently replaceable.

kvspace

Addressing and memory. One C ABI; shm and durable backends must match byte for byte.

layout

The o0 compiler. Parses source and writes the KV tree — no optimization, no IR.

runtime

Pure interpretation: fetch, decode, execute, route. Extensions live at /lib/<opcode>.

Three steps to a running program.

1 · Install


curl -fsSL https://raw.githubusercontent.com/array2d/kvlang/master/install.sh | sh

2 · Run


./bin/kvlang -c 'println("hello, world")'    # inline mode (entry init)
