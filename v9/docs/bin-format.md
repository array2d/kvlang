# `.bin` 产物格式

> 快照：2026-11-12。范围：`/lib/<pkg>·<func>.bin` 的 body 布局。
> 权威上游：`runtimec/include/kvlang/binrwir.h`（op 字位段、`binrwir_group_t`）、
> `runtimec/binrwir/README.md`（产物布局三段）、`v9/docs/runtime-data.md`（执行期四句柄）。

本文只定 v9 **写出**什么。runtimec 怎么读是它的事；但不能有第二种读法，所以凡是
「读方必须怎么理解」的地方，这里都写成规范句。

## 一、key 与 XValue

```
key       /lib/<pkg>·<func>.bin
langtype  [8N]uint8          N = 格数
attr      tag 1 = 上述 langtype（由构造器/写路径写入）
body      8N 字节，N 个 cell，小端
写入       kvspaceRealloc（唯一写原语），body 由 v9 填
```

**`langtype` 不是装饰**：`[8N]uint8` 把「body 是 8 字节格的数组」这件事写在类型里，
使 `.bin` 与普通 array 走同一条读取路径——runtimec 不需要知道「这是编译器产物」。
选择 `uint8` 而不是 `[N]uint64`：后者要求调用方按 8 字节元素解释，而 binrwir 的
cell 是**位段结构体**，不是整数。

## 二、body 三段

```
cell 0           goto：next_distance = 入口指令格下标
cell 1..k        字面量区：常量原始字节，按 8 字节格铺开
cell k+1..N-1    指令流：每条指令 = [读格…][op 字][写格…]
```

- **cell 0 是 goto**，不是占位：取指从 cell 0 开始，靠它的 `next_distance` 跳过字面量区。
  这样字面量区长度可变而不影响取指——执行器不需要知道「字面量有多长」这条元信息。
- `k` = 1 + 字面量格数；**指令流起点 = `k`**，写在 cell 0 的 `next_distance`。
- 字面量区**只放 8 字节对齐的原始字节**；不等宽的部分补零（见 §五）。

## 三、op 字位段

`binrwir_t`，一格 8 字节，小端，位序从低位排：

```
opcode16 | read_count4 | write_count4 | next_distance8 | reserved32
```

| 字段 | 含义 |
|---|---|
| `opcode` | `runtimec_v9_binrwir_opids.yml` 的 opid（当前 1..1845，16 位内） |
| `read_count` | 本条指令**紧跟其后**的读格数 |
| `write_count` | 读格之后紧跟的写格数 `< 4` |
| `next_distance` | 到**下一条 op 字**的距离（格数，见 §六） |
| `reserved` | 恒 0；非零即非法（与 head 的 padding 同规矩） |

**`write_count` 上限 3**（4 位但 v9 不许写 4）：op 字自身占一格，读写格共 3 格时已用满
一条 4 格组；4 个写参的指令在 rwir 层不存在，写成 4 会被读方当作「有 4 个写格」从而
与下一条 op 字错位。

## 四、读写格顺序

```
[读格 × read_count][op 字][写格 × write_count]
```

**读在前、写在后，中间夹 op 字**——这是 `binrwir_group_t` 的切法，`read_count`/
`write_count` 是唯一依据，没有分隔符。

读写格的来源是 layout 的 `[s0, s1]` 槽：

| s1 | 角色 |
|---|---|
| `< 0` | 读参，`s1 = -1, -2, …` 按出现顺序 |
| `> 0` | 写参，`s1 = 1, 2, …` |
| `= 0` | op 字本身（body 前 5 字节是 `[nr][00][nw][00][00]`，其后是算子名） |

**`-1` 在前还是 `-2` 在前**：按 `s1` 的**绝对值**升序（`-1, -2, -3`）。layout 的槽名
天然是这个顺序，v9 只排序、不重排语义——重排会让指令的操作数含义与明文 rwir 分叉。

## 五、操作数格编码：一律放引用

一格 8 字节，**从不放值本身，只放引用**：

```
kind 2 位 + payload 62 位
```

| kind | 含义 | payload |
|---|---|---|
| 0 | **字面量格** | 该常量在 body 内的**格号** |
| 1 | **kvspace 引用** | 值区偏移（布局槽 / 静态 key）；载入期加基址 |
| 2 | **addrbuf 索引** | 帧内索引；建帧期写、执行期取地址 |
| 3 | **分支目标** | `s0`（指令序号），不是格地址 |
| 正交 | **deref 位** | kind 之外单独一位；kind 0/1/2 都可能带 `*` |

**为什么一律放引用**（用户裁决）：全宽常量（int64/uint64/float64）与格内 tag 位天然
冲突——内联方案要么丢 2 位、要么给 float64 开特例。而「操作数一律是引用」只有
**一条规则**：handler 零分支，地址无关性统一（存偏移、载入期加基址）。代价是每个
常量多占一格，可接受。

**寄存器不进操作数格**：`pcs0`、`stack` 是执行期上下文里的寄存器，若出现在 opid
签名里，**不占 kind、不计入 `read_count`/`write_count`**。handler 按 opid 签名
知道它该从上下文取。典型：`kvspace·resolve(key, stack)` 的读格只有 key
（`read_count = 1`），`stack` 由上下文提供。

**不做格内角色 tag**：角色（值/位置/坐标）不单独编码——kind 只区分「引用从哪来」，
角色的语义差异由 opid 签名承担。多一层 tag 会让同一件事有两个来源。

### 五之二、addrbuf 解析表协议

**为什么帧局部必须走 kind = 2**：帧局部（`i`、`_1`、`_2`、`_6`、`*[0,1]`）在编译期
**只有名字，没有实体 key**——它们的存储是帧，建帧期才分配。所以编译期给不出
「值区偏移」，只能给一个索引，让建帧期去填。

**索引分配**：v9 为每个帧局部访问点分配一个索引，按 `s0` 顺序、**同名去重**。
iops 的 6 项：

```
0: i        1: _1       2: _2
3: _6       4: *[0,1]   5: *[0,-1]
```

操作数格 `kind = 2, payload = 索引`。

**解析表放在字面量区开头**：

```
cell 1          表项数 N
cell 2 .. 2+N-1 每项 = 该访问点对应 layout 槽 body 的**值区偏移**（8 字节）
```

**不复制 key 文本**：表项直接引用 layout 槽（body 是 `名字\0langtype`），与「不存
字面量副本」一致。载入期用 `base + offset` 读文本，读到 NUL 得名字。

**建帧期**：

```
对每项 i：
  文本 = base + 表项[i]            /* 读 layout 槽 body，到 NUL 为止 */
  名字 = 剥掉 `*` 前缀（layout 写的是 `*[0,1]`）
  地址 = resolve(stack 锚点 + 相对 key 名字)
  addrbuf[i] = 地址
```

**`*` 前缀在建帧期剥掉，但 deref 位保留、不在建帧期折叠**：
`*[0,1]` 的 `*` 说明「这是位置不是值」，但 `_p1` 这类**临时 Ptr 由 `resolvekey` 在
运行期写入**，建帧期解析出的地址会过期。所以 deref=1 时 addrbuf 存的是**槽地址**，
handler 在执行期读 Ptr body 再 resolve。

**`kind = 1` 留给编译期已知的布局槽 / 静态 key**：iops 用不到，先实现留空。

## 六、`next_distance` 单位

**单位是「格数」，从本条 op 字到**下一条指令的 op 字**的距离**。

```
本条 op 字在格 p，下一条 op 字在格 q  ⇒  next_distance = q − p
```

**读写格由 op 字里的 `read_count`/`write_count` 界定**，不靠 `next_distance` 定位：
执行器在 op 字前后各取 count 格，落点只回答「下一条的 op 字在哪」。这样 `next_distance`
是一个与读写格数无关的纯前进量——若让它指「下一条起始格」，那就把「前进多远」与
「本条占几格」耦合起来，读方要先解 count 才能算落点，多一层依赖。

- 一条指令占 `1 + read_count + write_count` 格，所以顺序执行时 `next_distance`
  = 上式的自然值；
- `reserved` 为 0 意味着 `next_distance` 最大 255 格——**跳远分支用 goto 链**，
  不靠大距离（见 §九）；
- **`next_distance = 0` 非法**：那会让执行器原地打转。v9 不产出它。

**cell 0 的 goto 用同一单位**：它到第一条指令的距离 = `k`（指令流起点），
即 `next_distance = 1 + 字面量格数`。

## 七、字面量区与常量

常量**内联在 cells 里**，不另开常量池（`runtime-data.md` §二）。

| 形态 | 放法 |
|---|---|
| 任何标量常量（int64/uint64/float64/int32/…/bool） | **占整整一格**，原始小端字节，窄类型高位补零 |
| key 文本（变长） | 原样铺在字面量区；引用方存「区起点字节偏移」 |

**一格一个，不分宽窄**：窄类型不挤进半格——统一占一格让「字面量格号」是一条有
意义的下标（`payload = 格号`），否则 `int8` 与 `int64` 的格子编号规则要分两套。

**操作数格引用它**：`kind = 0`、`payload = 字面量格号`。执行期 `cells + 格号*8`
就是这个常量的地址——**多一次跳转，换来一条规则**（§五）。

**key 文本不占整格**：它是变长字节，塞进 8 字节格的规则会与「格号即下标」冲突。
它在字面量区按字节铺开，引用方（`kind = 1` 的 kvspace 引用）直接用值区偏移。

## 八、`pcs0++` 的插入形态

v9 在**每两条 op 之间**插入一条 `pcs0++`：

```
opid  = add_uint32_uint32_uint32
读格  = [pcs0 地址, 常量 1 的地址]
写格  = [pcs0 地址]
```

- `pcs0` 是**寄存器**（`runtime-data.md` §三），不进操作数格——但 `add` 的一条指令
  需要两个读格一个写格，所以 `pcs0` 以**地址**形式出现在格子里，这是「寄存器作
  操作数」的唯一形态；
- 常量 1 是 `uint32`，占一格、低 4 字节、高位补零；
- **插入位置**：每条指令之后、下一条指令之前。所以顺序执行时
  `next_distance = 1(op) + read + write + (1 + 2 + 1)(pcs0++)`。

**只插在顺序执行的步末**（裁决 3）：

- 一条普通 op 之后 → **插**（它自己顺序执行完毕）；
- 一条**控制转移**（`goto` / `branch` / `return`）之后 → **不插**：它们自己写 pc，
  跟一条 `pcs0++` 会让步边界错位。

判据是「这条 op 执行完后 pc 会不会自然前移」，不是「它在不在一组的末尾」。

**这是编译产物，不是执行器行为**：`grouprun` 不自增 `pcs0`（README §「本目录的内容」）。

## 九、控制流

| rwir | binrwir | 编码 |
|---|---|---|
| `goto(_label)` | `goto` | `next_distance` 直接指目标格的**绝对格号**？否——见下 |
| `br(cond, _t, _f)` | `branch` | 两个目标写在**读格**里 |
| `return` | `return` | 无操作数 |
| `=` | `C·memcpy` | 见 §十 |

**`goto`/`branch` 的目标存 `s0`，不存地址**（裁决 1）：layout 已经把它解析成
`int64:<指令序号>`（`iops-slots.txt` 里 `goto(_while_3)` 的读格是 `int64:4`）。
所以目标操作数格是 `kind = 3, payload = s0`。

**执行器按 s0 处理，不按格地址**——崩溃恢复要的是 s0，格地址对恢复没有意义。

两条轴，别混：

| 轴 | 谁维护 | 用途 |
|---|---|---|
| `s0 → 格下标` | 载入期建表，**函数级**（可跨 group） | 分支目标落在哪一格 |
| `next_distance` | 编译期写进 op 字 | **只负责顺序前进**，不承担跨指令跳转 |

- 融合后允许 `s0` 空洞，**不许稠密化**——稠密化会让 s0 与 layout 的指令序号脱钩，
  崩溃恢复对不上；
- 目标 `s0` 不在表里 → **载入期报错**，不猜、不就近取；
- JIT 出口表同样按 `s0` 对齐。

**为什么要这个中间层**：`next_distance` 是相对值（相对值让 `.bin` 与绝对地址无关，
同一份产物可被任意载入位置使用）；而 layout 给的是指令序号（相对值，但与格布局无关）。
两者之间必须有一步换算，那一步是 v9 的职责。

**越界**：`next_distance` 只有 8 位。若换算结果 > 255，v9 **报错不产出**——
不发明「大跳转」指令，也不悄悄拆成 goto 链（那会改变指令序号语义）。

## 十、`=` 展开为 `C·memcpy`

`=` 在 rwir 是整值复制，在 binrwir 没有同名指令（README §「handler 按组放置」）。

```
opid = C·memcpy
读格 = [src 地址, byte_count 地址]
写格 = [dest 地址]
```

`byte_count` 是**定宽类型**的元素宽度（int64→8、bool→1、`[4]int64`→32）。

**变宽类型（`[]char/utf8`、`[]T`）暂不实现**：宽度要在运行期从 head 读，
那需要一条「读 head.bodylen 并作为 memcpy 长度」的指令，而 opid 表里没有。
方案待定（见 §十二）。

## 十一、iops 的逐格输出（验收基准）

11 条指令，layout 给的 `[s0,s1]` → 本格式的格序列（含插入的 `pcs0++`）：

| cell | 内容 |
|---|---|
| 0 | `goto`，`next_distance = 1 + 字面量格数` |
| 1..k | 字面量：`0`、`1`、`4`(=`_while_3`)、`7`(=`_do_4`)、`11`(=`_exit_5`) |
| k+1.. | 指令流 |

指令流（`→` 后为格数，`[r]`/`[w]` 标注读/写格）：

```
= :  [r:int64:0] [op:memcpy] [w:*[0,1]]                                  + pcs0++
= :  [r:int64:1] [op:memcpy] [w:i]                                       + pcs0++
goto: [r:int64:4] [op:goto]                                              + pcs0++
= :  [r:*[0,-1]] [op:memcpy] [w:_1]                                      + pcs0++
le : [r:i] [r:_1] [op:le] [w:_2]                                         + pcs0++
br : [r:_2] [r:int64:7] [r:int64:11] [op:branch]                          + pcs0++
= :  [r:*[0,1]] [op:memcpy] [w:_6]                                       + pcs0++
add: [r:_6] [r:int64:1] [op:add] [w:*[0,1]]                              + pcs0++
add: [r:i]  [r:int64:1] [op:add] [w:i]                                   + pcs0++
goto: [r:int64:4] [op:goto]                                              + pcs0++
return: [op:return]                                                       + pcs0++
```

**格数**：按上表逐条累加即得 `N`；`N = 1 + 5(字面量) + Σ(1+read+write+4(pcs0++))`。

## 十二、待定

已裁决、不再是待定（2026-11-12）：操作数一律放引用（§五）、`goto`/`branch` 存 s0
（§九）、`pcs0++` 只插顺序执行步末（§八）、寄存器不占格（§五）。

仍未决：

1. **变宽类型 `=`**（`[]char/utf8`、容器）：memcpy 长度是运行期事实，需要一条读 head
   的指令或 `kvspace·resolve` 的变体。opid 表目前没有。**本轮不做**，单独报方案。
2. **`kind = 2`（addrbuf 索引）的建帧期写入协议**：谁在什么时候把哪些访问点写进
   `addrbuf`，索引如何分配。iops 不需要（它只用 kind 0/1/3），但动态 key 需要。
3. **`kind = 1` 的「静态 key」与「布局槽」是否要分**：两者都是「值区偏移」，
   但失效语义不同（静态 key 永不变，布局槽随 Realloc 搬移）。若不加区分，
   搬移后要不要重解析由谁负责？
